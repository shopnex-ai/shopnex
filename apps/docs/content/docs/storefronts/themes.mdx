Bundled themes: **ks-bootshop** (default, Bootstrap), **storeplate**, **maison** (editorial, serif type), **shopco** (bold fashion). Theme names follow Shopify's Liquid objects, so Shopify theme developers feel at home.

```txt
themes/<id>/
  theme.json             ThemeDefinition: settings, section types, default pages, styles
  layout/theme.liquid    every page: {{ content_for_header }} in <head>, {{ content_for_layout }} in <body>
  templates/             index, collection, product, page, 404
  sections/<type>.liquid one per section type in theme.json
  snippets/              for {% render 'name' %}
  locales/               the theme's text: en.default.json, fr.json, pt-BR.json…
  assets/                served at /shopnex/assets/<id>/…, linked with {{ 'file' | asset_url }}
  src/theme.css          → assets/theme.css (Tailwind)
  src/theme.ts           → assets/theme.js (esbuild: TypeScript, npm packages, React islands)
```

<Callout type="warn">
  `id` in `theme.json` must match the folder name and stay stable: shops' customizations are stored under it.
</Callout>

1. Create the folder under `templates/storefront/themes/`.
2. Add it to `themes/index.json` (the first entry is the default).
3. Run `pnpm dev`. It rebuilds `assets/theme.css` and `assets/theme.js` on change; templates and `theme.json` are read on every request in dev.

Built assets are build output and are not committed.

## Sections and blocks

A page is a list of **sections** the merchant adds, hides and reorders in the theme editor. A theme renders them with `{% sections 'home' %}` (the sections of the page `home` in `theme.json`), each from `sections/<type>.liquid`. Inside it, `section` has `id`, `type`, `settings`, `blocks` and `block_order`, as in Shopify.

A section type can declare **blocks**: repeatable items inside it (a slide, an announcement, a link). The merchant adds, hides, removes and reorders them under the section in the editor, and edits each one's own settings.

```json
"announcement-bar": {
  "name": "Announcement bar",
  "max_blocks": 12,
  "settings": [{ "id": "speed", "label": "Seconds per message", "type": "range", "min": 3, "max": 10, "default": 5 }],
  "blocks": {
    "announcement": {
      "name": "Announcement",
      "settings": [
        { "id": "text", "label": "Text", "type": "text", "default": "Welcome" },
        { "id": "link", "label": "Link", "type": "url" }
      ]
    }
  }
}
```

```liquid
{%- for block in section.blocks -%}
  <p {{ block.shopify_attributes }}>
    {%- if block.settings.link != blank -%}<a href="{{ block.settings.link }}">{{ block.settings.text }}</a>{%- else -%}{{ block.settings.text }}{%- endif -%}
  </p>
{%- endfor -%}
```

- A block has `id`, `type`, `settings` and `shopify_attributes`; print `{{ block.shopify_attributes }}` on its element so the editor's preview can outline it when it is picked.
- `max_blocks` limits a section's blocks (up to 50). A block type's own `limit` limits how many of that type fit.
- Hidden blocks are left out of `section.blocks`. A block whose type the theme no longer has, or past a limit, is skipped, so an older saved page still renders.
- A page's default sections in `theme.json` can list their `blocks`, each `{ "id", "type", "settings" }`.

A setting can carry `"show_if": "<id of another setting>"`: the editor then shows it only while that setting has a value, for example a logo's width once there is a logo. It changes what the editor lists, nothing the theme reads.

### Changing a theme's structure

A saved theme keeps what merchants stored under the ids a theme declares: its settings, sections, block types and their settings. Removing or renaming one, or moving settings into blocks, would make that content silently stop showing, so a change like that comes with a **SQL migration** that moves the saved data, once, for every shop, when the app is upgraded.

1. Make the change in `theme.json` and the Liquid.
2. Create the migration: `pnpm --filter @shopnex/db exec drizzle-kit generate --custom --name=what_it_does`, and write the SQL in the file it makes (in `modules/db/migrations`). It changes the `draft` and `published` documents of `shop_themes` for the theme. Migration `0053_theme_documents_to_blocks.sql` is an example, and the `shopnex_theme_*` functions it creates (move numbered settings into blocks, split a one-per-line text into blocks, move an old setting into a block) are there to reuse.
3. Test it the way `modules/db/tests/theme-documents-migration.test.ts` does: the real migrations up to the one before, an old-format document, then the migration.
4. Open the pull request with the `breaking-theme-change` label.

A pull request is checked against its base branch (`.github/workflows/theme-compat.yaml`, like the API compatibility check): adding things is fine, and a removed or renamed setting, section or block type, or a removed theme, fails unless the pull request carries the `breaking-theme-change` label and adds a migration. A path the theme lists in `removed` (for example `"removed": ["sections/hero/settings/old_id"]`; a path covers what is under it) is a removal on purpose, with no content to move. To run the check locally: `pnpm --filter shopnex-storefront themes:compat`.

Themes that are not part of this repository get no automatic migration of what their merchants saved: a change like that needs the merchant to reapply their settings.

### Global sections

`{% section 'announcement-bar' %}` renders one section wherever you put it, usually in the layout, and the merchant edits it once for every page. Its settings and blocks are stored on the page `static` (declare it in `pages` of `theme.json` with the sections it starts with, and give the section type `"limit": 1`): the tag renders the section there with that id, else the first of that type. A global section the page does not list shows with its defaults, and one the theme lists that a theme saved earlier lacks (a footer that became editable later) is added with its defaults when the saved theme is read, so the editor lists it too.

### Liquid from Shopify themes

Sections written for Shopify's Liquid mostly render as they are: `section.settings`, `section.blocks`, `block.settings`, `block.type`, `block.id`, `block.shopify_attributes` and `{% sections %}` and `{% section %}` work the same. The `{% schema %}` at the end of a Shopify section file is ignored: a ShopNex theme declares its settings, blocks and styles in `theme.json`, not in the Liquid file.

## Text in several languages

A theme keeps the text it writes itself ("Add to cart", "Your cart is empty") in `locales/`, not in the templates. `en.default.json` is the theme's own wording and the fallback; `fr.json`, `pt-BR.json`… translate it. The files are nested JSON, read as dotted keys:

```json
{
  "cart": {
    "empty": "Your cart is empty",
    "items": { "one": "{{ count }} item", "other": "{{ count }} items" },
    "discount": "Discount ({{ code }})"
  },
  "js": { "cart": { "close": "Close cart" } }
}
```

In a template, `{{ 'cart.empty' | t }}` writes the text in the visitor's language (`localization.language`). Keyword arguments fill `{{ placeholders }}` and, with `count`, pick the plural form by the language's own rules:

```liquid
{{ 'cart.items' | t: count: cart.item_count }}
{{ 'cart.discount' | t: code: discount.code }}
```

- A region uses its own file, then its language's (`pt-BR` → `pt`), then the default's. A key a language has no text for falls back to the default **key by key**, so a half-translated theme never shows blanks. A key the theme has no text for shows `translation missing: key`.
- The text of a section is the merchant's, set in the theme editor: translate the template and snippet text, not the section settings.
- Keys under `js` are for the theme's scripts. The page embeds them in the visitor's language, and a script reads them with `t('js.cart.close')` from `@shopnex/storefront-sdk/i18n` (same placeholders and plurals).
- A theme that ships text in several languages is worth a test that every key it uses exists. The bundled themes have one (`templates/storefront/tests/theme-locales.test.ts`).
